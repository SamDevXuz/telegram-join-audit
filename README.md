# telegram-join-audit

Движок для поиска накрутки в заявках на вступление в закрытый Telegram-канал,
**когда размеченных данных нет**.

Задача, из которой это выросло: 965 заявок, часть из них — ферма аккаунтов,
часть — живые люди. Разметки нет и взяться ей неоткуда. Внешнего эталона
«нормального аккаунта» тоже нет: то, что нормально для канала про крипту
в Москве, ненормально для канала про ремонт в Ташкенте.

Подробный разбор метода и цифры с реальной выгрузки —
[в статье на vc.ru](https://vc.ru/id6131565/3169657-kak-vyyavit-feykovye-akkaunty-v-zayavkah-na-telegram-kanal).
Здесь лежит сам код, которым эти цифры считались.

## Главная идея

Привычная эвристика — искать «пустые» профили: нет аватарки, нет username.
На реальных данных она работает **в обратную сторону**:

```
органический фон канала:   аватарка 61,5%   username 47,1%
сессии массового залива:   аватарка 99-100% username 95-99%
```

Ферма аккуратнее живых людей. У живого человека может не быть аватарки,
потому что ему всё равно. У аккаунта, который готовили на продажу,
аватарка есть всегда — это часть товарного вида.

Отсюда то, что переопределяет всю задачу:

> **Нельзя искать признаки «плохого аккаунта». Нужно искать признаки
> однородности группы.**

Один аккаунт из фермы неотличим от живого человека. Двести аккаунтов из
одной партии — отличимы, потому что они слишком похожи друг на друга.

Второе следствие: **эталон берётся не снаружи, а из той же выгрузки.**
Заявки, не попавшие ни в один всплеск, объявляются органическим фоном
канала — это и есть base rate, с которым сравнивается всё остальное.

## Признаки

| | Что смотрит | Где в коде |
|---|---|---|
| 1. Однородность сессии | время прихода + состав профилей | `_sessions`, `UNIFORMITY_GAP` |
| 2. Генератор в username | только текст username | `is_generated`, `split_username` |
| 3. Даты первой аватарки | дни массовой заливки фото | `BATCH_SHARE`, `HUMAN_PHOTOS` |
| 4. Кластеры user ID | близкие ID = общая регистрация | `_id_clusters` |

Признаки 1 и 2 **полностью независимы**: первый не смотрит на текст,
второй не смотрит на время. На реальной выгрузке 608 из 615 аккаунтов
со сгенерированным username (98,9%) оказались внутри сессий залива.
Согласие двух независимых измерений — это то, что здесь заменяет
отсутствующий ground truth.

Решение принимается только по **групповым** признакам:

```python
flagged_users = uniform_users | family_users | cluster_users
```

Индивидуальный скор считается и показывается, но на решение не влияет.
«Этот аккаунт выглядит подозрительно» — не аргумент. «Эти 523 аккаунта
пришли за семь минут и на 99% одинаковы» — аргумент.

## Использование

```bash
pip install -r requirements.txt
```

Движок не ходит в Telegram сам — он принимает уже выгруженный список.
Данные берутся через MTProto (нужны права администратора в канале):

```python
from telethon.tl import functions, types

res = await client(functions.messages.GetChatInviteImportersRequest(
    peer=channel, requested=True, offset_date=None,
    offset_user=types.InputUserEmpty(), limit=100, q="",
))
```

Дальше:

```python
import analyzer

analyzer.init()
scan_id = analyzer.start_scan(channel_id)

analyzer.add_requests(scan_id, [
    # user_id, username, first_name, last_name, request_date(ISO, UTC),
    # has_photo, is_premium, is_scam, is_fake, is_bot, last_seen, access_hash
    (123456789, "userpn40838", "Dilshod", None, "2026-09-28T07:14:02+00:00",
     1, 0, 0, 0, 0, None, None),
])
analyzer.finish_scan(scan_id, "done", telegram_count=965, fetched_count=965)

rep = analyzer.analyze(analyzer.scan_rows(scan_id))

print(rep.total, len(rep.flagged_users))
for w in rep.windows:
    print(w.count, w.photo_rate, w.username_rate, w.uniform)
```

Признак 3 требует отдельного прохода по профилям (~0,35 с на аккаунт):

```python
photos = await client(functions.photos.GetUserPhotosRequest(
    user_id=user, offset=0, max_id=0, limit=10,
))
analyzer.save_photo_info([(user_id, photos.count, oldest_date_iso, now_iso)])
```

После этого `analyze` сам подхватит `photo_count` и `photo_date`
через `scan_rows`.

## Пороги

Все в `config.py`, с комментариями. Ключевые:

```python
BURST_MIN_ABS   = 8       # минута «горячая» от стольких заявок
BURST_FACTOR    = 4       # или во столько раз выше медианы
UNIFORMITY_GAP  = 0.25    # отрыв сессии от фона, в долях
FAMILY_MIN      = 8       # размер семейства username
HUMAN_PHOTOS    = 5       # белый список по числу фото
```

## Ограничения — честно

**Нет ground truth.** Precision и recall привести не с чем. Всё, что есть, —
согласованность независимых признаков. Это сильный аргумент, но не метрика.

**Пороги подобраны на одном наборе данных.** Риск переобучения на одну
ферму полностью реален. На вашем канале числа почти наверняка другие.

**Метод ловит группу, а не аккаунт.** Отдельно взятый помеченный аккаунт
не доказан как фейк. Доказана аномальность партии, в которую он попал.

**Медленный залив метод обходит.** Если лить по чуть-чуть, в темпе фона,
в течение нескольких суток, признак 1 не сработает — всплесков не будет.
Останутся username и даты аватарок, то есть половина силы. Это самая
очевидная линия обхода, и она не закрыта.

**Нужен закрытый канал с заявками.** На открытом канале по ссылке
исходных данных не существует.

## Что было выброшено

Четыре признака, которые красиво разделяли выборку и оказались мусором.
Самая полезная часть истории — в статье. Коротко:

- **Ритм времени** (82% против 22%) — мерил плотность потока, а не её
  природу. При пуассоновском потоке λ заявок в секунду вероятность
  «соседа в ту же секунду» равна `1 - e^(-λ)` и при заливе ~98% просто
  по определению.
- **Совпадение username с именем профиля** — вышло наоборот: 70% у фермы
  против 46% у живых. Ферма генерирует имя и username из одного источника.
- **Эмодзи в имени** — признак настоящий, но поменял бы решение по
  одному аккаунту. Сложность не окупается.
- **Кластеры user ID** — оставлены в коде с пометкой, что ловят только
  свежесозданные партии. На выдержанной ферме не дали ничего.
